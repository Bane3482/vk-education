# План реализации HW1: текстовая игра

## Основания и цель

План составлен по условию в `hw1.md`, текущему коду в `game/` и тестам в `game/main_test.go`. В тестах два сценария, всего 35 шагов.

Цель — пройти тесты и выполнить требование расширяемости: добавление комнат, предметов, мебели и дверей должно требовать изменения конфигурации в `initGame`, а не специальных условий в обработчиках команд.

`main_test.go` изменять нельзя. Типовой объём решения из условия — 300–400 строк; консольный ввод необязателен.

## Оценка текущей структуры

Полезные решения, которые стоит сохранить:

- Выделены игрок, мир, комнаты, переходы и предметы.
- Мебель позволяет группировать предметы при осмотре: «на столе», «на стуле».
- У двери предусмотрено отдельное состояние блокировки.
- Инициализация мира отделена от обработки команд.

Основная проблема — структура раздроблена на много пакетов, но пока почти не содержит поведения и контрактов между объектами.

| Текущая конструкция | Проблема | Рекомендация |
|---|---|---|
| Пустые интерфейсы `Room`, `Item`, `Player`, `World` | Принимают любые значения, но не предоставляют полезных методов | Использовать конкретные типы; интерфейсы вводить при появлении реального контракта |
| `Room.Items` и `Furniture.Items` | При хранении предметов в обоих местах потребуется синхронизация | Хранить предметы в мебели, искать их через методы комнаты |
| Один `Room.Description` | Вход и осмотр требуют разных описаний | Разделить описание входа и описание осмотра |
| `Transition.From`, `To`, `Destination` | Назначение последних двух полей неочевидно | Явно разделить название выхода и комнату назначения |
| Закрытое поле `Transition.enter` без конструктора | Не определён способ связать переход с дверью из другого пакета | Добавить конструктор или упростить организацию пакетов |
| `Backpack.inventory` | Нет операций поиска и добавления | Определить владельца инвентаря и реализовать операции над ним |
| Отдельные `Table` и `Chair` | Пока отличаются только названиями | Использовать общий тип мебели с заданной подписью |
| `CommandHeader` и отдельный пакет интерфейсов | Пока добавляют слои без полезного поведения | Заменить обычными обработчиками команд |

Метод `GetItem(id string) *items.Item` не удовлетворит текущему интерфейсу `player.Backpack`, где требуется `GetItem(id string) player.Item`: возвращаемые типы методов в Go должны совпадать.

Файл `game/furniture/chair.go` сейчас пустой. При сохранении этого файла проверка всех пакетов через `go test ./...` вызовет ошибку разбора: нужен хотя бы корректный `package` либо удаление ненужного файла.

## Рекомендуемая организация файлов

Для объёма HW1 достаточно нескольких файлов в одном `package main`:

```text
game/
  main.go          — initGame, handleCommand, необязательный ввод команд
  game.go          — Game, регистрация и выполнение команд
  world.go         — World, Transition, Door
  room.go          — Room, Furniture, поиск и удаление предметов
  item.go          — Item, свойства предмета
  player.go        — Player, экипировка и инвентарь
  commands.go      — пять общих обработчиков
  main_test.go     — существующие тесты без изменений
```

Текущие пакеты можно сохранить, но потребуется заранее определить зависимости и экспортируемые методы. Для этой задачи важнее ответственность объектов, чем количество пакетов. При переходе к одному пакету оставшиеся ненужные заготовки следует убрать, чтобы `go test ./...` проверял только актуальный код.

## Порядок реализации

### 1. Определить состояния и их владельцев

- Игрок хранит текущую комнату, экипировку и инвентарь.
- Мебель хранит оставшиеся в комнате предметы.
- Дверь хранит состояние открыта/закрыта.
- Комната хранит мебель, выходы и доступные объекты взаимодействия.
- Игра объединяет игрока, мир и обработчики команд.

Не хранить отдельно количество взятых предметов или готовые описания содержимого. Эти данные вычисляются из текущего состояния.

Инвариант: предмет находится либо в комнате, либо в инвентаре, либо в экипировке. Отказ в выполнении команды не изменяет состояние.

### 2. Реализовать минимальную модель объектов

| Сущность | Данные |
|---|---|
| `Game` | Игрок, мир, обработчики команд |
| `World` | Комнаты по идентификатору |
| `Player` | Текущая комната, экипировка, инвентарь по идентификатору предмета |
| `Room` | Описание входа, функция описания осмотра, мебель, выходы, объекты взаимодействия |
| `Furniture` | Подпись вроде `на столе`, упорядоченный список предметов |
| `Item` | Идентификатор, название, возможность надеть, способность предоставить место для хранения |
| `Transition` | Название выхода, комната назначения, необязательная дверь |
| `Door` | Состояние открыта/закрыта |
| Объект взаимодействия | Правила применения предметов к нему |

Возможность надеть предмет определяется его свойствами. Обработчик `надеть` не должен проверять конкретное название `рюкзак`.

Для вывода мебели, предметов и выходов использовать срезы: порядок обхода `map` не гарантирован, а тесты сравнивают ответы целиком. Мапы использовать для поиска комнат, предметов в инвентаре и обработчиков команд.

### 3. Реализовать операции над предметами

Комнате нужны операции поиска предмета с указанием мебели, где он находится, и удаления предмета. Игроку нужны операции проверки инвентаря, добавления предмета и экипировки.

При успешном взятии или надевании предмет удаляется из мебели. При отказе он остаётся на месте.

Это должно обеспечить:

- исчезновение рюкзака со стула после надевания;
- исчезновение ключей и конспектов со стола после взятия;
- ответ `нет такого` при повторном взятии ключей;
- сохранение ключей на столе после ответа `некуда класть`.

### 4. Реализовать общий вывод содержимого комнаты

Алгоритм:

1. Обойти мебель в заданном порядке.
2. Пропустить мебель без предметов.
3. Соединить названия предметов каждой группы через `, `.
4. Добавить подпись мебели и соединить группы через `, `.
5. Если все группы пусты, использовать описание пустого состояния комнаты.

Для жилой комнаты из этого алгоритма должны получаться:

```text
на столе: ключи, конспекты, на стуле: рюкзак
на столе: ключи, конспекты
на столе: конспекты
пустая комната
```

Не создавать отдельные условия для каждой комбинации предметов.

### 5. Разделить описание входа и осмотра

| Комната | Описание входа | Описание осмотра |
|---|---|---|
| Кухня | `кухня, ничего интересного` | Описание кухни, содержимое стола и текущая задача |
| Комната | `ты в своей комнате` | Текущее содержимое мебели или `пустая комната` |
| Коридор | `ничего интересного` | Можно использовать такое же описание |
| Улица | `на улице весна` | Можно использовать такое же описание |

Общий код добавляет к основному тексту:

```text
. можно пройти - <названия выходов через запятую>
```

Для осмотра можно использовать поле-функцию `Describe func(*Game) string`. Особенное описание кухни задаётся функцией в `initGame`, общее описание содержимого — методом.

Закрытая дверь не убирает улицу из списка выходов: проход существует и показывается, но движение через него запрещено.

### 6. Создать переходы и дверь

Исходный граф:

```text
кухня   → коридор
коридор → кухня, комната, улица
комната → коридор
улица   → домой
```

Название выхода и комната назначения — разные данные. Выход `домой` может вести в коридор, хотя комнаты с названием `домой` нет.

Возвращение с улицы тестами не проверяется. Назначение `домой → коридор` — выбранное поведение модели.

Создать дверь для перехода из коридора на улицу. Переход и объект взаимодействия `дверь` должны ссылаться на один экземпляр состояния двери. Если дверь используется и обратным переходом, он получает ту же ссылку.

### 7. Реализовать разбор и диспетчеризацию команд

Сохранить внешние функции, которые вызывают тесты:

```go
func initGame()
func handleCommand(command string) string
```

`handleCommand` разбивает ввод на слова, находит обработчик первого слова и передаёт оставшиеся аргументы.

Допустимая таблица обработчиков:

```go
map[string]func([]string) string{
    "осмотреться": ...,
    "идти":        ...,
    "надеть":      ...,
    "взять":       ...,
    "применить":   ...,
}
```

Это мапа названий действий, а не полных команд с готовыми ответами. Последний вариант запрещён условием.

Использовать `strings.Fields` для обработки лишних пробелов. Проверять число аргументов до обращения к ним. Неизвестная команда возвращает `неизвестная команда`.

Для пустого ввода и неполных команд можно выбрать тот же ответ. Тесты это поведение не определяют.

### 8. Реализовать пять общих обработчиков

| Команда | Последовательность |
|---|---|
| `осмотреться` | Получить описание осмотра текущей комнаты, добавить выходы |
| `идти X` | Найти выход, проверить дверь, изменить комнату, вернуть описание входа |
| `надеть X` | Найти предмет, проверить возможность надеть, экипировать, удалить из мебели |
| `взять X` | Найти предмет, проверить место для хранения, перенести в инвентарь |
| `применить X Y` | Проверить инвентарь, найти объект в текущей комнате, выполнить правило применения |

Требуемые ответы:

| Ситуация | Ответ |
|---|---|
| Неизвестная команда | `неизвестная команда` |
| Нет выхода с названием X | `нет пути в X` |
| Проход заблокирован дверью | `дверь закрыта` |
| Рюкзак успешно надет | `вы надели: рюкзак` |
| Нет места для хранения | `некуда класть` |
| Предмет отсутствует в комнате | `нет такого` |
| Предмет X успешно взят | `предмет добавлен в инвентарь: X` |
| Предмета X нет в инвентаре | `нет предмета в инвентаре - X` |
| Нет подходящего объекта или правила применения | `не к чему применить` |
| Ключи применены к двери | `дверь открыта` |

Для `идти` при отказе игрок остаётся в текущей комнате.

Для `взять` сначала искать предмет, затем проверять место для хранения. Это выбранный порядок: сочетание отсутствующего предмета и отсутствующего рюкзака тестами не уточняется.

Для `применить` сначала проверять инвентарь. Поэтому `применить телефон шкаф` возвращает `нет предмета в инвентаре - телефон`, а `применить ключи шкаф` — `не к чему применить`.

### 9. Настроить взаимодействия через конфигурацию

У объекта взаимодействия можно хранить правила вида:

```go
UseRules map[string]func(*Game) string
```

В `initGame` зарегистрировать у двери правило для ключей: открыть дверь и вернуть `дверь открыта`.

Обработчик `применить` только ищет объект и правило. Конкретные названия `ключи` и `дверь` находятся в конфигурации мира.

Ключи после применения остаются в инвентаре: следующий шаг теста использует их для шкафа.

При добавлении другой двери или взаимодействия должен меняться только `initGame`. Не дублировать правила применения одновременно в нескольких структурах без необходимости.

### 10. Реализовать полную инициализацию и задачу кухни

Каждый вызов `initGame` создаёт заново всё изменяемое состояние:

- игрок начинает на кухне;
- рюкзак ещё не надет;
- инвентарь пуст;
- чай находится на кухонном столе;
- ключи и конспекты находятся на столе в комнате;
- рюкзак находится на стуле;
- дверь закрыта.

Создавать новые мапы, срезы и экземпляры двери. Функции взаимодействия должны ссылаться на объекты новой игры. Второй сценарий не должен получать состояние первого.

Начальный ответ кухни при осмотре:

```text
ты находишься на кухне, на столе: чай, надо собрать рюкзак и идти в универ. можно пройти - коридор
```

После сбора вещей:

```text
ты находишься на кухне, на столе: чай, надо идти в универ. можно пройти - коридор
```

Тесты проверяют изменение после надевания рюкзака и взятия обоих предметов. Они не определяют, как должна выглядеть задача в промежуточных состояниях.

Рекомендуемое правило: рюкзак собран, когда он надет, а ключи и конспекты находятся в инвентаре. Проверку разместить в функции описания кухни, заданной в `initGame`. Не добавлять эту конкретную логику в общий обработчик `осмотреться`.

### 11. Проверить решение

Из папки `solutions/hw1/game` выполнить:

```bash
gofmt -w .
go test -v
go test ./...
go vet ./...
```

Если в репозитории настроен линтер, выполнить и его проверку. На момент составления плана `run_lint.sh` и конфигурация `.golangci*` в просмотренной части проекта не обнаружены.

Проверить:

- проходят оба сценария исходных тестов;
- ответы совпадают по порядку, пробелам и пунктуации;
- неуспешные команды не изменяют состояние;
- повторный `initGame` полностью сбрасывает игру;
- обработчики команд не содержат условий по названиям конкретных комнат и предметов;
- комнату, предмет на мебели и дверь с другим ключом можно добавить через `initGame`;
- все оставшиеся пакеты компилируются.

Консольный ввод через `bufio.Scanner` добавить последним, если он нужен. При распределении кода по нескольким файлам запускать приложение через `go run .`.
